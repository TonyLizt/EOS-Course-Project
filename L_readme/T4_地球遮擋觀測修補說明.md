# T4：地球遮擋觀測修補說明

## 給隊友的簡短說明

T4 的問題不在 Cesium 是否「看得到」任務點，而在排程可行性判定。舊場景的 `observation_windows` 是用錯誤的軌道歷元語義產生；排程器以前只確認任務時間落在預計算窗口內，因此即使衛星位於地球另一側，也可能把任務排進正式結果。

修補方式是在公共約束層增加一次獨立的完整曝光幾何檢查：依衛星軌道歷元計算每秒 ECEF 位置，再以任務目標的 WGS84 位置計算仰角。曝光起點、終點及中間每一秒都必須在目標地平線上；任何一個採樣點低於容差，就以 `earth occluded during exposure` 拒絕。

這項檢查同時接在：

1. 候選生成入口，避免演算法浪費時間評估已被地球遮擋的候選。
2. `ConstraintModel` 最終可行性核驗，防止其他演算法、舊候選或外部輸入繞過第一層。

所以不是把某個任務寫死，也沒有根據 Cesium 畫面猜測是否可見；所有演算法和 Controller 的正式核驗都使用相同規則。

## 問題原因

原本的判定鏈大致是：

```text
場景 observation window
        ↓
演算法選擇窗口內時間
        ↓
ConstraintModel 檢查時間、資源、衝突
        ↓
接受任務
```

這條鏈隱含假設「場景窗口一定正確」。但 legacy 場景的軌道 epoch 曾被錯誤解析，導致窗口時間與真實衛星位置不一致。典型例子是：

- `SCD_1_22490` 執行 `M003` 時，目標仰角低於 `-70°`。
- `GPM-CORE_39574` 執行 `M018` 時，目標仰角低於 `-40°`。

兩者都代表衛星和目標之間被地球遮擋，不能進行光學觀測。Cesium 的使用者相機、衛星模型朝向和任務連線只負責顯示，不能作為排程物理可行性的判定來源。

## 修補過程

### 1. 建立共用幾何守門器

新增 [`schedulers/observation_geometry.py`](../schedulers/observation_geometry.py)，主要流程為：

1. 使用場景內的半長軸、偏心率、傾角、近地點幅角、升交點赤經、平近點角及 epoch，進行確定性的 Kepler 傳播。
2. 依 GMST 將衛星 ECI 位置轉成 ECEF。
3. 依 WGS84 將目標經緯度與高度轉成 ECEF。
4. 以目標的局部 `up` 向量計算衛星仰角。
5. 從曝光起點到終點以 1 秒取樣，且明確包含兩個邊界。
6. 最低仰角小於 `-0.05°` 時拒絕，微小負容差只用來吸收簡化 ECI/ECEF 計算在地平線邊界的數值誤差。

此模組是安全守門器，不取代 Orekit 的正式窗口生成。仰角結果使用快取，以降低多個演算法反覆檢查相同時間點的成本。

### 2. 在候選生成階段提前拒絕

在 [`algorithms/candidate_pool.py`](../algorithms/candidate_pool.py) 的 `push_candidate()` 呼叫 `validate_observation_interval()`。若整段曝光不可見，就不把該 assignment 放入候選池。

窗口如果帶有更細的 `time_step`，檢查會採用 `min(1 秒, window.time_step)`，不會因窗口解析度更高而降低驗證精度。

### 3. 在統一約束層再次核驗

在 [`schedulers/constraint_model.py`](../schedulers/constraint_model.py) 的 `is_feasible_assignment()` 再執行同一檢查。

這一層才是安全邊界：即使某個演算法沒有使用共用 candidate pool，或 assignment 來自舊結果/外部程式，只要進入正式核驗，就不能繞過地球遮擋規則。

### 4. 重算錯誤場景，而不是刪除約束

啟用正確遮擋判定後，legacy 窗口大量失效，TCR 曾由約 92%～100% 降到約 45%～60%。這不是新約束過嚴，而是舊窗口與真實軌道不同步。

因此後續以正確 epoch 和 Orekit 重算六個 `epoch_fixed_v1` 場景，並透過 SHA、物理驗證及 release sidecar 控制新實驗只能選用正式修正版。沒有藉由移除遮擋判定來恢復 TCR。

目前發佈結果：

- 四個 small 場景：seed 1/42/99 均為 100% TCR。
- medium S1：95% / 94% / 95%。
- medium S2：98% / 98% / 98%。
- medium 各有兩個任務缺少足夠長的物理窗口，因此保留為未完成，不偽造 100%。

## 驗證

[`tests/test_observation_geometry.py`](../tests/test_observation_geometry.py) 覆蓋：

- 已知錯誤案例 `SCD_1_22490 / M003` 被拒絕。
- 已知錯誤案例 `GPM-CORE_39574 / M018` 被拒絕。
- 即使 assignment 位於 legacy observation window 內，`ConstraintModel` 仍會拒絕被地球遮擋的曝光。

[`tests/test_epoch_fixed_scenarios.py`](../tests/test_epoch_fixed_scenarios.py) 另驗證六個正式修正版場景能通過發佈門檻，並且 TCR 的恢復沒有繞過遮擋檢查。

可執行：

```bash
python -m unittest -v \
  tests.test_observation_geometry \
  tests.test_epoch_fixed_scenarios
```

## 相容性與注意事項

- 若合成測試或舊資料完全沒有軌道/目標幾何欄位，結果標記為 `checked=False` 並維持相容，不會無條件破壞非幾何測試。
- 真實場景具備完整幾何資料時，遮擋檢查必須執行，不能以「窗口已預先計算」為理由略過。
- 此修補不改變衛星本體姿態、固定鏡頭方向、Cesium 使用者相機或任務收益，只決定觀測 assignment 是否具備基本視線條件。
- 後續若替換傳播模型，候選端和最終核驗端必須繼續共用同一公開函式，避免兩套幾何語義再次分歧。
