# T4：地球遮擋觀測修補說明

## 給隊友的簡短說明

T4 的問題不在 Cesium 是否「看得到」任務點，而在排程可行性判定。舊場景的 `observation_windows` 是用錯誤的軌道歷元語義產生；排程器以前只確認任務時間落在預計算窗口內，因此即使衛星位於地球另一側，也可能把任務排進正式結果。

修補分成兩層：排程器只接受具有可信窗口生成證據的保守窗口；Controller 在正式寫入結果前，再以同一場景、計畫、Orekit 資料與程式身份執行連續曝光認證，只有 `CONTINUOUS_PASS` 才能持久化。`REJECTED`、`INCONCLUSIVE`、錯誤或超時都 fail closed。

另保留一個每秒 ECEF/WGS84 仰角診斷器，用來重現及定位明確的地球遮擋案例。它會檢查曝光起點、終點與中間樣本，但有限取樣不能證明樣本之間持續可見，因此不接管正式發布權限。

正式鏈路的兩個關鍵入口是：

1. 候選生成及 `ConstraintModel` 共用 `planning_exposure()`，拒絕無可信來源或超出保守窗口的候選。
2. Controller 使用不可由 Worker 偽造的認證 receipt 核驗完整曝光，通過後才寫入正式計畫與指標。

所以不是把某個任務寫死，也沒有根據 Cesium 畫面猜測是否可見。這項檢查是額外的「明確違規即拒絕」守門器；正式發布仍由最新版連續曝光認證負責，有限取樣不會被冒充為連續性證明。

## 問題原因

原本的判定鏈大致是：

```text
場景 observation window
        ↓
演算法選擇窗口內時間
        ↓
ConstraintModel 檢查時間、資源、衝突
        ↓
接受任務
```

這條鏈隱含假設「場景窗口一定正確」。但 legacy 場景的軌道 epoch 曾被錯誤解析，導致窗口時間與真實衛星位置不一致。典型例子是：

- `SCD_1_22490` 執行 `M003` 時，目標仰角低於 `-70°`。
- `GPM-CORE_39574` 執行 `M018` 時，目標仰角低於 `-40°`。

兩者都代表衛星和目標之間被地球遮擋，不能進行光學觀測。Cesium 的使用者相機、衛星模型朝向和任務連線只負責顯示，不能作為排程物理可行性的判定來源。

## 修補過程

### 1. 建立共用幾何守門器

新增 [`schedulers/observation_geometry.py`](../schedulers/observation_geometry.py)，主要流程為：

1. 使用場景內的半長軸、偏心率、傾角、近地點幅角、升交點赤經、平近點角及 epoch，進行確定性的 Kepler 傳播。
2. 依 GMST 將衛星 ECI 位置轉成 ECEF。
3. 依 WGS84 將目標經緯度與高度轉成 ECEF。
4. 以目標的局部 `up` 向量計算衛星仰角。
5. 從曝光起點到終點以 1 秒取樣，且明確包含兩個邊界。
6. 最低仰角小於 `-0.05°` 時拒絕，微小負容差只用來吸收簡化 ECI/ECEF 計算在地平線邊界的數值誤差。

此模組是安全守門器，不取代 Orekit 的正式窗口生成。仰角結果使用快取，以降低多個演算法反覆檢查相同時間點的成本。

### 2. 候選生成使用可信窗口門禁

在 [`algorithms/candidate_pool.py`](../algorithms/candidate_pool.py) 先呼叫 `planning_exposure()`。窗口的場景 SHA、生成版本、源码身份和步長證據不可信時，不會進入候選池；對舊 v2 網格還會保守扣除一個實際掃描步長。

### 3. 統一約束與 Controller 再次核驗

[`schedulers/constraint_model.py`](../schedulers/constraint_model.py) 的 `is_feasible_assignment()` 會再次套用 `planning_exposure()`，防止其他演算法繞過候選池。Controller 隨後執行更強的連續曝光認證；離散約束通過只代表規劃可行，不代表可正式發布。

### 4. 重算錯誤場景，而不是刪除約束

啟用正確遮擋判定後，legacy 窗口大量失效，TCR 曾由約 92%～100% 降到約 45%～60%。這不是新約束過嚴，而是舊窗口與真實軌道不同步。

因此後續以正確 epoch 和 Orekit 重算六個 `epoch_fixed_v1` 候選，並保留 SHA、物理抽樣及 TCR 診斷。合併最新版連續曝光規則後，舊 sampled-release sidecar 不足以放行，候選不會出現在新實驗選擇器，也不會隱藏 legacy。沒有藉由移除遮擋判定來恢復 TCR。

舊離散口徑的診斷結果（不是正式發佈結果）：

- 四個 small 場景：seed 1/42/99 均為 100% TCR。
- medium S1：95% / 94% / 95%。
- medium S2：98% / 98% / 98%。
- medium 各有兩個任務缺少足夠長的物理窗口，因此保留為未完成，不偽造 100%。

## 驗證

[`tests/test_observation_geometry.py`](../tests/test_observation_geometry.py) 覆蓋：

- 診斷器確認 `SCD_1_22490 / M003` 明確被地球遮擋。
- 診斷器確認 `GPM-CORE_39574 / M018` 明確被地球遮擋。
- 即使 assignment 位於 legacy observation window 內，正式規劃來源門禁仍會拒絕不可信窗口。

[`tests/test_epoch_fixed_scenarios.py`](../tests/test_epoch_fixed_scenarios.py) 另驗證六個候選不會繞過目前的可信窗口來源門檻，legacy 場景仍可供選擇。

可執行：

```bash
python -m unittest -v \
  tests.test_observation_geometry \
  tests.test_epoch_fixed_scenarios
```

## 相容性與注意事項

- 若合成測試或舊資料完全沒有軌道/目標幾何欄位，結果標記為 `checked=False` 並維持相容，不會無條件破壞非幾何測試。
- 真實場景具備完整幾何資料時，遮擋檢查必須執行，不能以「窗口已預先計算」為理由略過。
- 此修補不改變衛星本體姿態、固定鏡頭方向、Cesium 使用者相機或任務收益，只決定觀測 assignment 是否具備基本視線條件。
- 後續若替換傳播模型，候選端和 Controller 認證端必須維持明確的證據版本與身份綁定，避免兩套幾何語義再次分歧。

相關提交位於分支 `fix/cesium-300s-consistency`；rebase 後提交雜湊已更新。核心幾何守門器與歷元修正候選都保留，但正式發布仍受連續曝光證據門檻阻擋。
