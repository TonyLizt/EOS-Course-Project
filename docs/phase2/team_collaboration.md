# 第二阶段组员协作规范

本文件供四位成员在同一仓库中开发、审核和集成使用。分工以《第二阶段实施计划说明书_审核稿》及本仓库 README 的项目分工为准。当前系统边界见[框架交接说明](framework_handoff.md)；算法接入见[算法接入说明](algorithm_integration.md)。

## 1. 每次更改的基本规则

1. **一项可审核的工作开一个新分支，最后通过 Pull Request（PR）合并。** 不直接在 `main` 开发或推送；已合并的分支不继续承载下一项工作。
2. **代码和对应文档放在同一个 PR。** 每次更改都要记录改了什么、为什么、如何验证以及尚有哪些限制。接口、数据库、算法、Worker、页面或实验协议发生变化时，必须同步更新对应专题文档；同时在根目录 `COURSE_SETUP.md` 写一条简短版本记录。纯文档更改也要说明更改内容。
3. PR 由至少一名未编写该改动的组员审核；涉及公共接口、数据库模式、运行状态或数据协议时，由李泽同确认集成影响。作者处理意见并确认检查通过后再合并；作者不自行绕过审核直接合并自己的 PR。
4. 一个 PR 尽量只完成一个明确目标。需要依赖另一个未合并的 PR 时，在说明中写明依赖和合并顺序，避免把其他人的改动混进本 PR。
5. 不提交母场景、大型模型、训练数据、虚拟环境、数据库、运行缓存、导出结果和临时文件。测试输出放在 `EOS_RUNTIME_DIR` 或系统临时目录，测试结束及时清理；输入场景保持只读。

## 3. 分支与 PR 流程

下列命令在**自己的仓库工作目录**执行，可在 Windows PowerShell 或 Ubuntu 终端中使用。不要把示例目录当成固定路径。开始前先确认当前状态；如果有未提交工作，先整理到自己的分支，不要用 `reset --hard` 清除。

```bash
git status
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feat/worker-ipc
```

上面的 `feat/worker-ipc` 只是示例，创建分支时应换成当前工作对应的名字，例如 `feat/algorithm-a`、`feat/result-comparison`、`fix/run-state-recovery` 或 `docs/data-protocol`。分支名称不代表所有权；实际负责人写在 PR 中。完成代码、文档和验证后，先检查差异，再提交并推送：

```bash
git status # 确认没有无关文件
git diff --check
git add -A
git commit -m "feat: 简述本次改动"
git push -u origin HEAD
```

如果开发期间 `main` 更新，先提交自己的工作，再在自己的分支运行 `git fetch origin` 和 `git merge origin/main`；有冲突时按 Git 提示逐个解决、完成合并提交，重新测试后运行 `git push`。不要在有未整理改动时强行切换分支或覆盖文件。

在 GitHub 选择 **base: `main`、compare: 自己的分支** 创建 PR。先核对差异中只有本项工作；填写下文的 PR 清单，邀请组员审核。审核通过且检查通过后再合并。合并后更新本地 `main`，下一项工作从更新后的 `main` 新开分支。不要在合并后继续往旧分支提交新功能。

如果当前 `feat/phase2-v0.2` 尚未合并到 `main`，依赖 v0.2 接口的工作可以先从该分支建立**临时依赖分支**，并在 PR 中标明依赖；待 v0.2 合并后，将 PR 的基线整理到最新 `main`，确认差异只含自己的工作，再请求合并。

## 4. 文档与改动记录如何同步

| 更改内容 | 同一 PR 中应更新的文档与证据 |
|---|---|
| HTTP 字段、状态码、运行状态、配置或 Controller 行为 | `docs/phase2/interface_design_target.md` 中对应目标与实现说明、`docs/phase2/framework_handoff.md`；必要时更新 README 的用户操作说明。目标稿与当前实现要明确区分。 |
| SQLite 表、字段、关系、迁移或删除规则 | `docs/phase2/database_current_v02.md` 的当前模式和 ER 图；涉及目标设计变化时同步 `database_design_target.md`。写明迁移与旧库保留策略。 |
| Worker/IPC、Daemon、取消、超时或恢复 | 对应模块设计文档或在 `docs/phase2/` 新建专题文档；写明消息/状态契约、进程边界和故障演示步骤。 |
| 算法 A/B/C/D | `docs/phase2/algorithm_integration.md` 的公共接入变化；各算法另建 `docs/phase2/algorithms/<algorithm-id>.md`，记录机制、版本、参数、依赖、可行性测试、种子和成对实验。算法 D 还需记录数据来源与划分、训练配置、模型哈希和训练/推理耗时。 |
| 场景或实验协议 | 在 `docs/phase2/` 的数据/实验专题文档记录来源、SHA-256、生成方式、训练/验证/测试划分、基线配置、指标口径和预算；不要将大型数据本体提交仓库。 |
| 页面、导出或可视化 | README 中用户能看到的操作变化，以及交接说明中的页面/API 边界；截图或演示记录只保留必要的小文件或链接。 |
| 依赖、安装命令、目录结构或运行方式 | README、相应 requirements 文件和交接说明。 |

**所有 PR** 还要在 `COURSE_SETUP.md` 顶部补一条简短记录：日期、模块/版本、主要变更、验证结果和已知限制。专题文档承载细节，`COURSE_SETUP.md` 用于追溯整体版本。若多人同时修改该文件，后合入者先更新分支并解决冲突，不覆盖先合入的记录。文档中的命令和路径应能在 Windows + WSL2 Ubuntu 22.04 环境复现。

## 5. 提交 PR 前的检查

- [ ] 当前分支不是 `main`，PR 目标为 `main`；差异中没有无关改动或生成文件。
- [ ] 受影响的专题文档和 `COURSE_SETUP.md` 已与代码一起更新；公开接口与实际实现一致。
- [ ] 新功能有针对性的验证；算法有固定种子小实例、可行计划核验和同场景成对实验记录。
- [ ] `python -m unittest discover -s tests -v` 通过；涉及运行链路时在 Ubuntu 中完成相应 HTTP/Worker/数据库闭环检查。无法运行的检查在 PR 中说明原因与影响。
- [ ] 公共接口、状态和数据库变更已通知相关负责人；数据库变更有显式迁移，不直接删改历史实验。
- [ ] 母场景、模型和临时输出没有进入提交；涉及输出路径的代码遵守当前数据源和输出目录规则。

建议在 PR 描述中使用以下结构：

```markdown
## 目的
这次改动解决什么问题。

## 改动
- 代码及行为变化
- 同步更新的文档

## 验证
- 命令、环境、结果；算法附场景哈希、种子和预算

## 接口与数据影响
- API/IPC/数据库/算法协议有无变化；迁移与兼容方式

## 已知限制与依赖
- 尚未覆盖的情况、依赖的其他 PR
```

## 6. 合并后的交接

PR 合并者确认 `main` 上的测试与浏览器闭环仍可运行，并把 PR 链接、合并提交及必要的复现实验信息补入相应记录。若发现回归，另开修复分支与 PR；不要直接修改 `main`。公共契约发生变化时，由李泽同通知受影响的组员同步分支。正式集成演示以合并后的 `main` 和记录的场景哈希为准。
